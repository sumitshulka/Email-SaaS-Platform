# BUILD A MULTI-TENANT EMAIL SENDING SAAS APPLICATION

## 1. PRODUCT OBJECTIVE

Build a production-ready, secure, multi-tenant SaaS web application for individual users to send personalized text-based emails to their own contact lists using their own email accounts.

The application is NOT intended to be a CRM, ERP, marketing automation platform, or enterprise campaign management system.

The core purpose is:

1. Individual user registration and authentication.
2. Subscription/package management.
3. User-owned SMTP/email account configuration.
4. Email account verification through OTP.
5. Contact list upload and management.
6. Contact segmentation/list creation.
7. Personalized email template creation using contact placeholders.
8. Scheduled sequential email sending.
9. Per-user hourly sending limits.
10. Email delivery/bounce tracking where technically supported.
11. Email history.
12. Basic user analytics.
13. Superadmin administration, configuration, payments and monitoring.

The system must be designed as a true MULTI-TENANT application.

Each individual user is a tenant.

A user's contacts, email accounts, templates, lists, campaigns, email history, subscription information and analytics must NEVER be accessible to another user.

---

# 2. IMPORTANT DEVELOPMENT PRINCIPLES

Build the application in a modular and production-oriented manner.

Do NOT create a fake/demo application.

Do NOT hard-code business rules that should be configurable by Superadmin.

Do NOT create unnecessary enterprise features.

Do NOT add CRM functionality.

Do NOT add lead management.

Do NOT add sales pipeline functionality.

Do NOT add invoicing/accounting functionality beyond subscription payment records.

Do NOT add team members or organization accounts in Phase 1.

Do NOT add HTML email designer in Phase 1.

Phase 1 email body should be TEXT based, with a controlled signature section supporting one image/logo.

Use clean APIs and service-layer architecture so future functionality can be added without rewriting the application.

# 8. SUBSCRIPTION ENFORCEMENT

A user MUST have an ACTIVE subscription to use the application.

Subscription states:

- Pending
- Active
- Expired
- Cancelled
- Failed
- Suspended

When subscription expires:

- User cannot send emails.
- User cannot create campaigns.
- User cannot upload additional contacts.
- User cannot perform normal application actions that require an active subscription.
- User should be redirected to Subscription page.
- Existing historical information should remain accessible where appropriate.
- User should be clearly informed that subscription renewal is required.

Do not delete user data when a subscription expires.

After successful payment:

- Create/update subscription.
- Set start date.
- Calculate expiry/next billing date based on package frequency.
- Store Razorpay payment/order/subscription references.
- Activate the user's account.

# 17. USER EMAIL VERIFICATION

When user configures a new email account:

1. Save configuration in pending/unverified state.
2. Generate OTP.
3. Send OTP using the configured email account where technically possible.
4. User enters OTP.
5. Verify OTP.
6. Mark email account as Verified.

Important:

Even if the user's login email was verified during registration, the configured sending email MUST be separately verified.

A new OTP must be generated for the sending account.

OTP:

- configurable expiry
- configurable maximum attempts
- resend cooldown
- hashed storage if possible
- one-time use
- invalidated after successful verification

# 28. SEQUENTIAL CAMPAIGN EXECUTION

Very important:

There must NOT be parallel campaign execution for the same user.

If User A schedules:

Campaign A at 10:00
Campaign B at 11:00

and Campaign A takes until 15:00:

Campaign B must wait until Campaign A completes.

The system must automatically activate Campaign B after Campaign A completes.

The user should see:

"Campaign queued. Your previous campaign is currently running. This campaign will start automatically after the previous campaign completes."

Implement this at the job/service layer, not merely in the UI.

A database/job locking mechanism must prevent duplicate execution.

# 79. TESTING

Create automated tests for critical business rules.

At minimum test:

### Tenant isolation

User A cannot access User B's:

- contacts
- campaigns
- templates
- email history
- email account

### Subscription

Inactive user cannot:

- create campaign
- send email
- upload beyond allowed functionality

### Hourly limit

100/hour means no more than 100 sends within the configured rolling/hourly window according to the implemented policy.

### Sequential campaigns

Campaign B cannot execute while Campaign A is running for the same user.

### Bounce

Hard bounce deactivates contact.

### Payment

Duplicate webhook must not create duplicate subscription.

### OTP

Expired OTP cannot verify email.

### Authentication

Invalid login attempts are rate limited.

### Credentials

SMTP and Razorpay secrets are never returned by APIs.

# 87. REPLIT AGENT WORKING STYLE

IMPORTANT:

Do not generate the entire application blindly in one pass.

First:

1. Analyze this specification.
2. Propose the architecture.
3. Create the database schema.
4. Create the project structure.
5. Implement authentication and roles.
6. Run tests.
7. Fix errors.
8. Then continue module by module.

After each major module:

- Run the application.
- Run relevant tests.
- Fix compilation/runtime errors.
- Verify database migrations.
- Verify API behavior.

Do not move forward while the previous foundational module is broken.

Keep business logic in reusable services.

Keep controllers/routes thin.

Keep database access in repository/service layers where practical.

Use TypeScript strict mode.

Use environment variables only for application-level secrets such as the master encryption key, database connection, session secret and deployment configuration.

Razorpay and SMTP credentials are intentionally configurable from the Superadmin UI and must be encrypted in the database.
